### Instrumentando o código — Decisão da Equipe

Vamos utilizar a biblioteca `prometheus-client`, já instalada no simulador Python,
para expor `/metrics` na porta 8000. O código usa `Counter` para leituras processadas
com sucesso (`iot_readings_total`) e erros de processamento
(`iot_processing_errors_total`), `Gauge` para valores instantâneos e `Histogram`
para o tempo de processamento. A biblioteca também expõe, no contêiner Linux,
CPU acumulada do processo (`process_cpu_seconds_total`) e memória residente
(`process_resident_memory_bytes`). O Prometheus coleta essas métricas a cada 15
segundos pelo Service interno do simulador. Não precisamos reimplementar a
instrumentação feita em 07/10; nesta entrega vamos utilizá-la no Grafana.

### Os 4 Dashboards Obrigatórios — Decisão da Equipe

Vamos publicar exatamente quatro dashboards, cada um com um painel de série
temporal: CPU, Memória, Erro na aplicação e Sucesso na aplicação. Todos usam o
Prometheus como fonte de dados, configurada automaticamente por provisioning.
CPU será expressa como porcentagem de um núcleo utilizado pelo processo Python;
Memória será o RSS do processo em bytes, exibido automaticamente em MiB pelo
Grafana; Erro será a quantidade de leituras rejeitadas por segundo; Sucesso será
a quantidade de leituras válidas processadas por segundo. Aplicaremos `rate()`
aos contadores para mostrar a atividade recente, em vez do total desde o início.
Os quatro dashboards serão versionados em JSON e montados por ConfigMap para
reproduzir a configuração em outra implantação.

### Golden Signals — taxa de erros

A taxa de erros mostra se o processamento está se deteriorando mesmo quando o
servidor ainda responde. Um crescimento das leituras rejeitadas, acompanhado de
queda no processamento bem-sucedido e aumento de CPU ou memória, ajuda a equipe
a investigar sobrecarga, dados inválidos ou defeitos no código antes que isso
comprometa os diagnósticos das oficinas. Também podemos calcular a proporção
`erros / (erros + sucessos)` para comparar períodos com volumes diferentes;
sem tentativas, essa proporção fica indefinida, e não significa 100% de sucesso.
Uma falha elétrica ou temperatura elevada detectada no veículo não é erro da
aplicação: se a leitura foi processada corretamente, conta como sucesso.
Os gráficos apoiam a investigação, mas não provam por si só a causa da falha.

## Arquitetura e decisões técnicas

```text
Simulador Python :8000/metrics
           | scrape a cada 15s
           v
Prometheus :9090 (armazenamento das séries)
           ^ consultas PromQL via HTTP interno
           |
Grafana :3000 -> quatro dashboards -> navegador via port-forward
```

Os arquivos `grafana/provisioning/` conectam a fonte de dados ao endereço
`http://prometheus.mecaniqa.svc.cluster.local:9090` e carregam os JSONs da pasta
`grafana/dashboards/`. O UID fixo `mecaniqa-prometheus` evita referências quebradas.
O manifesto `k8s/grafana.yaml` declara Deployment, Service ClusterIP, PVC de 1 GiB,
requests/limits e probes. O Grafana roda como usuário 472 e recebe a credencial
por Secret gerado no cluster, sem senha versionada. A estratégia `Recreate`
evita duas instâncias escrevendo no mesmo PVC durante atualização.
O Deployment do Prometheus também usa `Recreate`, pois seu armazenamento TSDB
deve ter apenas uma instância escritora durante os reinícios previstos no script.

| Dashboard / arquivo | Consulta PromQL | Interpretação |
| --- | --- | --- |
| CPU / `cpu.json` | `100 * sum(rate(process_cpu_seconds_total{job="iot-simulator"}[$__rate_interval]))` | 100% corresponde a um núcleo. Não é porcentagem do limite de CPU nem CPU total do nó. |
| Memória / `memoria.json` | `sum(process_resident_memory_bytes{job="iot-simulator"})` | RSS do processo Python, não memória de todo o nó/contêiner. |
| Erro / `erro.json` | `sum(rate(iot_processing_errors_total{job="iot-simulator"}[$__rate_interval]))` | Rejeições por segundo. Zero é esperado com entradas válidas e coleta ativa. |
| Sucesso / `sucesso.json` | `sum(rate(iot_readings_total{job="iot-simulator"}[$__rate_interval]))` | Leituras válidas por segundo, incluindo diagnósticos de falhas no veículo. |

São métricas do processo da aplicação, suficientes para este ambiente de uma
réplica. Monitorar todos os Pods/nós exigiria coleta adicional, por exemplo
cAdvisor e descoberta de Pods. A coleta estática pelo Service não é adequada
para observar individualmente várias réplicas. CPU e memória indicam utilização
de recursos; não substituem toda a medição de saturação. Os quatro Golden Signals
clássicos são latência, tráfego, erros e saturação: os quatro títulos exigidos
pelo caderno não são uma reprodução literal dessa lista.

## Executar e demonstrar

Pré-requisitos: Docker Desktop em modo Linux, kubectl, Kind em
`.local/bin/kind.exe`, espaço livre e acesso aos registries para baixar imagens.
O script usa exclusivamente o contexto local `kind-mecaniqa`.

Na raiz do repositório:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/deploy-local.ps1
$env:KUBECONFIG = Join-Path (Get-Location) '.local/kubeconfig'
kubectl --context kind-mecaniqa -n mecaniqa get deploy,pods,svc,pvc
kubectl --context kind-mecaniqa -n mecaniqa port-forward service/grafana 3000:3000
```

`ExecutionPolicy Bypass` vale apenas para esse processo PowerShell. O script
constrói as imagens, cria/reutiliza o Kind, sincroniza os ConfigMaps, cria o Secret
se ausente, aplica os recursos e aguarda os rollouts, incluindo Grafana.

Em outro terminal, obtenha a senha local:

```powershell
$env:KUBECONFIG = Join-Path (Get-Location) '.local/kubeconfig'
$encodedPassword = kubectl --context kind-mecaniqa -n mecaniqa get secret grafana-admin -o jsonpath='{.data.password}'
[Text.Encoding]::UTF8.GetString([Convert]::FromBase64String($encodedPassword))
```

Abra `http://localhost:3000`, usuário `admin`, senha do Secret. Não mostre a senha
na gravação. Em Dashboards, abra a pasta **MecaniQA OAT 2** e os quatro dashboards.
Aguarde ao menos um minuto para obter amostras suficientes para `rate()`.
O painel de erro em zero é um resultado normal com leituras válidas;
**No data** exige verificar coleta e intervalo, não equivale a zero erros.

Em outro terminal, confira a coleta:

```powershell
kubectl --context kind-mecaniqa -n mecaniqa port-forward service/prometheus 9090:9090
```

Abra `http://localhost:9090`, verifique o target `iot-simulator` e consulte
`up{job="iot-simulator"}`: esperado 1 quando a coleta funciona.

Com os dois port-forwards ativos, execute a validação e exportação dos dashboards
realmente carregados no Grafana:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/validate-monitoring.ps1
```

O script confere a saúde do Grafana e da fonte de dados, a presença dos quatro
dashboards, suas consultas e as amostras no Prometheus. Salva as respostas e
os dashboards exportados em `docs/evidencias/2026-10-14/`, sem credenciais.

Para obter capturas da interface, `scripts/capture-dashboards.py` usa Playwright
e o Microsoft Edge instalado no Windows. Essa dependência é opcional no computador
de validação e não foi adicionada ao contêiner do simulador:

```powershell
.local/venv/Scripts/python.exe -m pip install playwright
.local/venv/Scripts/python.exe scripts/capture-dashboards.py
```

As capturas mostram os valores do momento da execução; não representam um teste
de estresse ou disparo de alarmes.

Para atualizar apenas o Grafana em um cluster já preparado:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/prepare-grafana.ps1
kubectl --context kind-mecaniqa apply --dry-run=server -f k8s/grafana-configmaps.yaml -f k8s/grafana.yaml
kubectl --context kind-mecaniqa apply -f k8s/grafana-configmaps.yaml -f k8s/grafana.yaml
kubectl --context kind-mecaniqa -n mecaniqa rollout restart deployment/grafana
kubectl --context kind-mecaniqa -n mecaniqa rollout status deployment/grafana --timeout=300s
```

## Exportar e versionar

Os JSONs em `grafana/dashboards/` são as definições importáveis e reproduzíveis.
Depois de criar alterações na interface, exporte o JSON pelo menu de exportação
do dashboard, preserve o UID da fonte de dados e substitua o arquivo correspondente.
Dashboards provisionados são controlados pelos arquivos: use uma cópia para
editar pela interface e depois atualize a definição versionada. Execute
`powershell -NoProfile -ExecutionPolicy Bypass -File scripts/sync-grafana-config.ps1`
para atualizar `k8s/grafana-configmaps.yaml` antes do commit e da implantação.
